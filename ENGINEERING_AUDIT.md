## 1. Project Overview

### Goal

Tizahab is a tourism planning platform targeting visitors and residents of **Riyadh, Saudi Arabia**. It helps users discover places (restaurants, museums, parks, malls, entertainment venues), set personal preferences, and receive a personalized daily itinerary generated by a rule-based recommendation engine.

### Target Users

- Tourists visiting Riyadh for the first time
- Residents seeking curated day-out suggestions
- Arabic and English speakers (bilingual UI: RTL/LTR supported)

### Core Product Concept

1. User registers and sets preferences: interests (food, culture, outdoor, shopping, entertainment), budget range, and preferred language.
2. The system filters its database of 3,090 real Riyadh places against those preferences.
3. A "Generate AI Plan" button produces a daily itinerary of up to 5 places, one per interest category.
4. Plans are visualised on a Google Map with time-slotted cards (9 AM, 2-hour increments).
5. Users can browse all places, filter them, and view individual event pages.

### App Roles and Interactions

**`accounts`** owns all identity concerns: signup, login, JWT issuance, password reset, and the `UserPreferences` model which is the source of truth for what each user is interested in and their budget. Every other app consumes `request.user.preferences` but does not write to it.

**`events`** owns the place catalogue. It exposes two API views: a general list (with optional search/category/date filters) and a personalised filtered view that reads the active user's preferences directly to narrow results. The `Event` model is the central shared entity — both `daily_plan` and the carousels on the home page read from it.

**`daily_plan`** owns itinerary logic. It calls `events.models.Event` via `daily_plan.services.generate_recommendations()`, which queries events by the user's interests and budget, then associates the resulting events with a `DailyPlan` record. The `DailyPlan` model holds a many-to-many relation to `Event`.

**`core`** provides cross-cutting concerns with no domain models: the `NoIndexMiddleware` (prevents authenticated pages from being indexed), the `google_maps_api_key` context processor (injects the Maps key only for authenticated users), and all management commands that populate the database.

## 3. Architecture Diagram

### Backend Request Flow

```
Browser
  │
  │  HTTP request (e.g. POST /api/daily-plan/generate/)
  ▼
Django WSGI (Gunicorn in production)
  │
  ├─ SecurityMiddleware          → HTTPS redirect, HSTS headers
  ├─ WhiteNoiseMiddleware        → Serves /static/ files directly (bypasses Django)
  ├─ SessionMiddleware
  ├─ CsrfViewMiddleware          → CSRF token validation
  ├─ AuthenticationMiddleware    → Session-based user attachment
  ├─ NoIndexMiddleware           → Appends X-Robots-Tag: noindex to dashboard routes
  │
  ▼
config/urls.py  (root URL dispatcher)
  │
  ├─ /api/auth/          → accounts.urls
  ├─ /api/events/        → events.api_urls
  ├─ /api/daily-plan/    → daily_plan.urls
  ├─ /events/            → events.page_urls
  ├─ /daily-plan/        → TemplateView (renders daily_plan.html)
  └─ /home/ /map/ etc.   → TemplateView (renders static templates)
  │
  ▼
DRF APIView / GenericAPIView
  │
  ├─ JWTAuthentication    → Validates Bearer token from Authorization header
  ├─ IsAuthenticated      → Rejects anonymous requests with 401
  │
  ▼
View logic
  │
  ├─ Serializer validation (e.g. date format, interests list, budget range)
  ├─ Queryset isolation   (filter(user=request.user) — users never see others' data)
  ├─ Service calls        (generate_recommendations() in daily_plan/services.py)
  │
  ▼
Django ORM
  │
  ├─ SQLite (development)
  └─ PostgreSQL (production via DATABASE_URL)
  │
  ▼
HTTP Response (JSON for API, HTML for page views)
```

### Frontend Flow

```
User opens browser → Django serves template (TemplateView or page view)
  │
  │  HTML is a "shell" — no server-side data injection into most pages
  │  (Exceptions: GOOGLE_MAPS_API_KEY injected via context processor)
  │
  ▼
Browser loads:
  ├─ TailwindCSS (CDN)
  ├─ Lucide icons (CDN unpkg)
  ├─ static/css/design-system.css    → CSS custom properties for theming
  ├─ static/js/api.js                → apiGet(), apiPost(), auth header injection
  └─ static/js/<page>.js             → Page-specific logic
  │
  ▼
DOMContentLoaded fires
  │
  ├─ Read JWT from localStorage
  ├─ If missing/expired → redirect to /login/
  │
  ├─ Fetch data via apiGet("/api/...")
  │     ├─ Adds Authorization: Bearer <token> header automatically
  │     ├─ On 401 → clears tokens, redirects to /login/
  │     └─ On error → throws Error with status + backend detail message
  │
  ├─ Render data into DOM (plain JS, no framework)
  │     ├─ Event cards (buildMiniCard, buildUpcomingCard)
  │     ├─ Daily plan time-slots (renderDailyPlan)
  │     └─ Google Map markers (renderDailyPlanMarkers)
  │
  └─ User interactions → apiPost() → backend response → re-render
        Example: "Generate AI Plan" → POST /api/daily-plan/generate/
                                    → renderDailyPlan(response)
```

### Theme and Language Switching

Both theme and language are purely client-side:

```
page load
  ├─ Inline <head> script reads localStorage("tz_theme") and localStorage("tz_lang")
  ├─ Sets data-theme="dark|light" on <html> before any paint (prevents flash)
  └─ Sets dir="rtl|ltr" and lang="ar|en" on <html>

Theme toggle button click:
  ├─ Calls toggleTheme(next)
  ├─ Writes to localStorage
  └─ Updates button emoji (🌙 / ☀️) immediately

Language button click:
  ├─ Calls applyLang(lang)
  ├─ Toggles .hidden on .nav-label-en / .nav-label-ar elements
  ├─ Switches font-family (Arimo → Cairo)
  └─ Writes to localStorage
```

## 7. Frontend Code Quality

### Template Analysis

All templates follow a two-base pattern:
- **`base_auth.html`**: Used by `landing.html`, `login.html`, `signup.html`. Provides gradient background, logo, and minimal JS.
- **`dashboard_base.html`**: Used by all authenticated pages. Provides sidebar navigation, top header (theme toggle, language toggle, avatar), and the main content area.

This structure is clean and avoids repetition for the common layout. The sidebar, language toggle, and theme toggle are implemented once and inherited across all dashboard views.

### JavaScript Architecture

The JS layer uses a **zero-framework, module-like pattern**: `api.js` is loaded first on every authenticated page and attaches helpers to `window`. Page-specific scripts (`daily_plan_integration.js`, `events.js`, `map.js`) then call those globals.

**Strengths:**
- `apiGet` and `apiPost` centralise all fetch logic — auth headers, 401 redirect, and error extraction happen in one place.
- `escapeHtml()` is used consistently in dynamic DOM injection — no raw `innerHTML` from user-controlled data.
- Category metadata (`CATEGORY_MAP`) is defined once in `api.js` and reused across all pages.
- Theme is applied before first paint via an inline `<head>` script, eliminating flash-of-wrong-theme.
- RTL/LTR switching is complete: `dir`, `lang`, font family, and nav label visibility all toggle correctly.

**Weaknesses:**
- **JWT stored in `localStorage`**: Vulnerable to XSS exfiltration. The correct approach for production is `httpOnly` cookies, but this requires a backend change to the token issuance flow.
- **No accessibility (a11y) attributes**: Interactive elements (sidebar links, toggle buttons, modals) lack `aria-label`, `aria-expanded`, `role`, or keyboard focus management.
- **No error boundaries**: If `apiGet` throws on the home page carousels, errors are silently swallowed (`catch { /* silent */ }`). This makes debugging carousel failures very difficult.
- **Dark mode CSS partially implemented**: The `design-system.css` defines CSS custom properties and a `[data-theme="dark"]` selector, but most templates use Tailwind utility classes (`bg-white`, `text-gray-600`) which do not respond to the data-theme attribute. Dark mode does not visually apply to most content areas.
- **No bundler or transpiler**: Scripts are served as individual files. On pages that load 3–4 JS files, there is no tree-shaking, minification, or cache-busting beyond WhiteNoise's content hash on `collectstatic`.
- **`preferences.html` is standalone**: It does not extend `dashboard_base.html`, meaning the sidebar and theme/language toggles are absent on the onboarding page. This creates a visual inconsistency.
- **Duplicate `DOMContentLoaded` listeners**: `daily_plan_integration.js` registers two separate `DOMContentLoaded` listeners (one for the plan page, one for the carousels). This is safe but harder to reason about.

### RTL/LTR

The language toggle correctly sets `dir="rtl"` and switches the body font to `Cairo`. Sidebar navigation labels switch between `.nav-label-en` and `.nav-label-ar` class visibility. However, **Tailwind's `ltr:`/`rtl:` variants are not used** in templates, meaning margin/padding directional alignment (e.g. `ml-64` for the sidebar offset) does not flip for Arabic users.

### Responsive Behaviour

The sidebar collapses to a hamburger menu on mobile (`lg:hidden` / `lg:translate-x-0`). The overlay and close button are implemented. The top header is compact on mobile (`sm:hidden` hides search on small screens). Tailwind grid classes are used consistently.

### Frontend Quality Score

**6.5 / 10**

> Clean base template inheritance and centralised API layer are significant positives. Deductions for: JWT in localStorage, incomplete dark mode in Tailwind classes, no a11y attributes, silent error suppression in carousels, and RTL directional layout not fully applied.

## 8. Backend Code Quality

### Views

Views follow DRF conventions consistently. `ListCreateAPIView` and `RetrieveUpdateDestroyAPIView` are used for standard CRUD. Custom logic is in `GenerateDailyPlanAPIView` (an `APIView` subclass), which handles date validation, preference checking, and service invocation with thorough error discrimination (400 vs 404 vs 500).

**Queryset isolation** is correctly enforced: every view that returns `DailyPlan` records filters by `user=self.request.user`. Events are not user-scoped (they are a shared catalogue, which is correct).

**`prefetch_related("events")`** is applied on list views for `DailyPlan`, preventing N+1 queries when serialising the M2M relationship.

**Logging** is used throughout: `logger.info` on plan creation/update, `logger.warning` on invalid input, `logger.error` on unexpected failures.

### Serializers

`SignupSerializer` validates password confirmation and uniqueness. `UserPreferencesSerializer` validates that interests are from the allowed set and that `budget_min ≤ budget_max`. `DailyPlanSerializer` uses `PrimaryKeyRelatedField` for events — efficient and correct.

`EventSerializer` is a standard `ModelSerializer` — all 21 fields are serialised, which is verbose but acceptable for a small dataset. There is no explicit field filtering per endpoint (e.g., the list view returns full event objects with descriptions and coordinates even when only title and category are needed for the carousel).

### Recommendation Engine (`daily_plan/services.py`)

The logic is clean and the return value contract is explicit: `None` means "no preferences", `[]` means "no matches", a list means success. Callers can distinguish all three cases. The function applies budget filters with `OR price IS NULL` to include free events, which is correct.

**Issue:** `generate_recommendations()` accepts a `date_str` parameter but does not use it. The parameter exists for API compatibility but is dead code inside the function body.

**Issue:** `.order_by("?")` is used to shuffle recommendations at the database level. On SQLite this is `ORDER BY RANDOM()`, which is fine. On PostgreSQL at scale it can cause a full table scan before shuffling — it does not use indexes efficiently.

### Management Commands

Three importers exist:
1. `import_tizahab_dataset.py` — primary importer, well-structured, uses `settings.BASE_DIR` for path resolution, prints progress every 500 records.
2. `fetch_outdoor_data.py` — seeds 30 hardcoded places first, then hits Overpass API with a single combined query. Gracefully handles timeouts.
3. `fetch_real_data.py` — legacy multi-query importer, now superseded, should be removed.

### Middleware

`NoIndexMiddleware` uses a simple prefix list approach. It correctly covers all authenticated routes. The approach is robust and easy to extend.

### Error Handling

The backend distinguishes error types correctly throughout:
- 400: Client error (bad date, missing preferences, invalid input)
- 401: Unauthenticated (handled by DRF/JWT)
- 404: No results for valid request
- 500: Unexpected server error

### Known Anti-Patterns

1. **No `@transaction.atomic` on plan generation**: `get_or_create` + `events.set()` are two separate DB operations. Under concurrent requests for the same user + date, a race condition could create two `DailyPlan` rows before the unique constraint fires, resulting in an `IntegrityError`. This should be wrapped in `@transaction.atomic`.
2. **`events.urls.py` is loaded but serves legacy routes**: The root `config/urls.py` correctly routes to `events.api_urls` and `events.page_urls`, but `events.urls.py` still exists and mixes both patterns. It is not included anywhere in the URL config but creates confusion for new developers.
3. **`itinerary` app dead code**: Removed from `INSTALLED_APPS` but migrations remain. The orphaned `itinerary_dailyplan` table sits in the database. This should be documented clearly or cleaned up.
4. **`core/views.py` and `core/urls.py` are stubs**: They contain placeholder code (`pass`) and are not wired into the URL config.

### Backend Quality Score

**7 / 10**

> Good DRF conventions, proper queryset isolation, explicit error discrimination, and comprehensive logging. Deductions for: missing `@transaction.atomic` on plan generation, dead `date_str` parameter, `ORDER BY RANDOM()` scaling risk, and leftover stub files.

## 11. Performance Risks

### N+1 Queries

- **`DailyPlanListCreateAPIView`** calls `prefetch_related("events")` — N+1 is avoided here. ✅
- **`DailyPlanRetrieveUpdateDestroyAPIView`** also uses `prefetch_related("events")`. ✅
- **`EventListAPIView`** and `EventRetrieveAPIView` return flat Event objects — no related traversal, no risk. ✅
- **`FilteredEventsAPIView`** reads `request.user.preferences` — this is a single extra query per request (the `UserPreferences` row). Acceptable at this scale.

### `ORDER BY RANDOM()`

`generate_recommendations()` uses `.order_by("?")` to shuffle events. On SQLite this is `ORDER BY RANDOM()`. On PostgreSQL:
- The database must read all matching rows before selecting the top N.
- With 2,924 food-category events, this performs a full index scan + sort on every plan generation request.
- **Mitigation:** Fetch a larger pool of candidates (e.g., 50), shuffle in Python with `random.sample()`, then slice to 5. This lets the query use the `category` index efficiently.

### Large Event Table

The Event table has 3,090 records. At this scale there are no meaningful query performance concerns. However:
- **`?search=`** uses `Q(title__icontains=...) | Q(description__icontains=...) | Q(location__icontains=...)`. `icontains` on SQLite is a full table scan. On PostgreSQL, consider `SearchVector` / `SearchRank` with a GIN index for meaningful search at 10,000+ records.
- **`category` + `date` composite index** exists and covers the most common filter combination.

### Pagination

- All API views use DRF's `PageNumberPagination` with `PAGE_SIZE=50`. This prevents unbounded queries. ✅
- The frontend carousels fetch `/api/events/` and slice the first 6 results client-side. This means 50 full event objects are fetched, serialised, and transmitted over the network to display 6 cards. A `?page_size=6` override or a dedicated lightweight endpoint would reduce this to ~88% less data.

### Static Files

WhiteNoise serves compressed (gzip/brotli) static files with content-hash cache-busting. This is production-ready for moderate traffic. For high traffic, a CDN (CloudFront, Cloudflare) in front of WhiteNoise is recommended.

### Database Connections

`conn_max_age=600` (10 minutes) and `conn_health_checks=True` are configured. This enables connection pooling at the Django layer, which is good for Gunicorn with multiple workers.

### Scaling Risks Summary

| Risk | Severity | Mitigation |
|---|---|---|
| `ORDER BY RANDOM()` on large datasets | Medium | Replace with Python-side shuffle |
| `icontains` search without full-text index | Medium | Add PostgreSQL `SearchVector` + GIN index |
| Carousels over-fetch (50 events for 6 cards) | Low | Add `?page_size=6` param or lightweight endpoint |
| No caching layer | Low | Add Redis (already in docker-compose) for recommendation results |
| Single Gunicorn process in default config | Medium | Set `--workers` to `2 * CPU_COUNT + 1` in production |

## 12. Known Issues & Technical Debt

### Bugs

1. **Dark mode incomplete**: The `data-theme="dark"` attribute is set on `<html>`, but most Tailwind utility classes (`bg-white`, `text-gray-600`, etc.) in templates do not respond to it. Only elements using CSS custom properties from `design-system.css` visually change. Dark mode is functional for colour tokens but broken for most layout elements.

2. **`date_str` unused in `generate_recommendations()`**: The function accepts `date_str` but does not apply it to the query. The parameter is accepted from the API for future use but currently has no effect, which could confuse developers expecting date-aware recommendations.

3. **No server-side auth on page routes**: Dashboard templates (`/home/`, `/daily-plan/`, etc.) are served as `TemplateView` with no `login_required` decorator. A user who knows the URL can access the HTML shell. Auth is only enforced at the API layer. This is acceptable for a SPA-style architecture but means a user without JS sees a blank page rather than a redirect.

4. **Favourites button is non-functional**: The events list page UI renders a favourites button, but there is no `Favourite` model, no API endpoint, and no JS handler. Clicking it does nothing.

5. **Notifications bell is decorative**: The bell icon in the header has a red dot badge but no backend connection.

### Technical Debt

1. **`events.urls.py` is dead code**: The file exists, mixes page and API routes, but is not included in `config/urls.py`. It should be deleted to avoid confusion.

2. **`fetch_real_data.py` is superseded**: The legacy Overpass importer was replaced by `fetch_outdoor_data.py` and `import_tizahab_dataset.py`. It should be removed.

3. **`core/views.py` and `core/urls.py` are stubs**: Both contain only `pass` or empty placeholder content and serve no purpose.

4. **`itinerary` app is orphaned**: Removed from `INSTALLED_APPS` but its migration and the resulting `itinerary_dailyplan` table remain in the database. Acceptable technically, but a new developer will be confused.

5. **`preferences.html` is a standalone page**: Does not extend `dashboard_base.html`. It has its own full `<html>` structure with hardcoded fonts and styles, making it drift from the design system over time.

6. **No API versioning**: All endpoints are at the root `/api/` with no version prefix. A future breaking change would require careful client coordination rather than a clean `/api/v2/` cutover.

7. **`django-tailwind` vs CDN Tailwind**: The project has `django-tailwind` installed (which compiles Tailwind via Node.js) but templates load Tailwind from CDN (`<script src="https://cdn.tailwindcss.com">`). This means compiled Tailwind output is not actually used in templates. The CDN version is slower (full Tailwind CSS loaded, not purged) and defeats the purpose of the `theme/` app.

## 15. Project Roadmap

### Immediate — Before Production Deployment

1. **Fix incomplete dark mode.** Audit all Tailwind utility classes in templates and replace with CSS custom property equivalents, or use Tailwind's `dark:` variant with the `class` strategy.
2. **Wrap plan generation in `@transaction.atomic`.** Prevents the race condition where two concurrent requests could attempt to create two `DailyPlan` rows for the same user + date.
3. **Replace `ORDER BY RANDOM()` with Python-side shuffle.** Fetch 20 candidates per category, shuffle in Python, slice to 1. Preserves index usage on PostgreSQL.
4. **Remove dead code:** Delete `events/urls.py`, `fetch_real_data.py`, `core/views.py`, and `core/urls.py`.
5. **Restrict Google Maps API key** in the GCP Console to the production domain HTTP referrer.
6. **Set `CSRF_TRUSTED_ORIGINS`** to the production domain before going live.
7. **Fix `preferences.html`** to extend `dashboard_base.html` for design consistency.
8. **Switch Tailwind from CDN to compiled output** using `django-tailwind`'s `npm run build`. This reduces page weight and purges unused classes.

### Short Term — 1–2 Weeks After Launch

1. **Implement Favourites.** Add a `Favourite(user, event)` model, a `POST/DELETE /api/favourites/<event_id>/` endpoint, and wire up the existing UI button.
2. **Add API versioning.** Introduce `/api/v1/` prefix to all endpoints to enable future non-breaking evolution.
3. **Improve search.** On PostgreSQL, add a `SearchVector` field to `Event` with a GIN index for full-text relevance ranking instead of `icontains`.
4. **Reduce carousel over-fetching.** Accept `?page_size=N` in `EventListAPIView` and use `?page_size=6` in carousel JS calls.
5. **Add test coverage for management commands.** Mock the Overpass API response in `fetch_outdoor_data` tests. Test `import_tizahab_dataset` against a temporary JSON fixture.
6. **Add `aria-label` and keyboard navigation** to sidebar, toggle buttons, and modal-like components.
7. **Profile page editing.** Add `PATCH /api/auth/profile/` endpoint for updating display name and avatar initial letter.

### Long Term — Future Features

1. **Move JWT to `httpOnly` cookies.** Eliminates the XSS token theft risk. Requires changes to token issuance views and the `api.js` layer (remove `Authorization` header injection; rely on cookies instead).
2. **Upgrade recommendation engine.** Incorporate user history, ratings, and time-of-day signals. Consider collaborative filtering for "users like you also enjoyed" suggestions.
3. **Real-time place data.** Integrate Google Places API or Foursquare for live operating hours, photos, and user reviews to supplement the static dataset.
4. **Booking integration.** Re-introduce booking links to restaurants and venues with real reservation URLs.
5. **Notification system.** Wire up the bell icon to a real notification model (e.g., "Your plan for tomorrow is ready", "New places added in your area").
6. **iOS/Android app.** The existing REST API is already app-ready. A React Native or Flutter client could reuse the API layer with minimal backend changes.
7. **CORS and SPA architecture.** If a separate frontend domain is introduced, add `django-cors-headers` and update the token strategy to `httpOnly` cookies with `SameSite=Strict`.
8. **Redis caching for recommendations.** Cache `generate_recommendations()` results per user for 30 minutes. Reduces database load when users re-generate plans repeatedly.
9. **Internationalisation beyond toggle.** Use Django's `i18n` framework for server-rendered strings rather than duplicate `.nav-label-en` / `.nav-label-ar` DOM elements.
